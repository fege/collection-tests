# TC-E2E-002: NetworkPolicy and ServiceMonitor ship together for scraping in default-deny namespace

**Objective**: Validate that both the ServiceMonitor and NetworkPolicy are created atomically when EvalHub is deployed, enabling Prometheus scraping in namespaces with default-deny ingress policies.

**Preconditions**:
- OpenShift cluster with RHOAI 3.5.EA1 and TrustyAI operator
- Test namespace (`opendatahub`) with default-deny ingress NetworkPolicy
- User-workload-monitoring enabled

**Test Steps**:
1. Verify the namespace has a default-deny ingress policy
   ```bash
   oc get networkpolicy -n opendatahub
   ```
2. Deploy an EvalHub CR with metrics enabled
   ```bash
   oc apply -f evalhub-metrics-enabled.yaml -n opendatahub
   ```
3. Wait for operator reconciliation (up to 60 seconds)
4. Verify both ServiceMonitor AND NetworkPolicy are created
   ```bash
   oc get servicemonitor -n opendatahub -l app=evalhub
   oc get networkpolicy -n opendatahub | grep evalhub
   ```
5. Verify the NetworkPolicy allows ingress from the monitoring namespace to the metrics port
6. Wait for Prometheus scraping (up to 90 seconds)
7. Verify the EvalHub scrape target is UP despite the default-deny namespace
   ```bash
   oc exec -n openshift-user-workload-monitoring prometheus-user-workload-0 -c prometheus -- \
     curl -s 'http://localhost:9090/api/v1/targets' | jq '.data.activeTargets[] | select(.labels.job | contains("evalhub")) | .health'
   ```

**Expected Results**:
- Both ServiceMonitor and NetworkPolicy are created when EvalHub is deployed
- The NetworkPolicy permits Prometheus ingress from the monitoring namespace
- Despite the default-deny ingress, Prometheus successfully scrapes EvalHub with target health `up`
